Monthly Payroll Cycle - Step-by-Step Change

How the Payroll Cycle Changes

Steps unchanged from as-is are shown in grey. Autonomous agent steps are highlighted in purple/amber. Step 5 is investigator-led - Claude Code skills are invoked on-demand, no autonomous pipeline. HITL gate shown in green.

7 stages 2 agents + 6 skills + 1 utility 1 HITL gate + 1 skills step
1
Payroll cycle opens in Payroll Aggregator Unchanged
Payroll team opens the cycle in Payroll Aggregator. HR / ERP System master data is already integrated - standard employee records flow automatically as they do today. Agent 1 is triggered at this point to begin its assignee analysis run in parallel.
2
Agent 1 - Assignee Tax Analysis Runs ★ Agent 1
Agent 1 reads all ~50 assignee records from HR / ERP System via MCP. Because the HR / ERP System integration (PG XML/pay group) can only route each employee to one country, assignee shadow payroll data and mobility inputs must be retrieved from supplementary sources - Mobility Advisor term sheets in Dropbox/Google Drive - via MCP tools. For each employee, the agent retrieves presence day counts, applicable tax treaties, prior-cycle treatment, and any host-country allowance changes (e.g. housing, cost-of-living) that feed back into home-country shadow adjustments. Claude Sonnet 4.6 with extended thinking (5-8k token budget) reasons through each multi-jurisdiction scenario and produces a structured tax treatment memo, citing every source used. Deterministic calculations (day counts, treaty lookups) use dedicated tools - never LLM arithmetic.
3
HITL Gate 1 - Tax Memo Review & Approval ✓ HITL Required
Payroll team (or tax advisor, if flagged by agent) reviews each memo via the /run-tax-cycle skill output. Each memo shows the recommended treatment, jurisdiction breakdown, treaty basis, and confidence level. The team approves, modifies, or rejects. No data is written to Payroll Aggregator until explicit approval. Escalation triggers include novel treaty combinations, missing presence data, and prior-treatment conflicts.
4
Payroll inputs submitted to External Partner Unchanged
Approved assignee tax treatments (from step 3) are entered into Payroll Aggregator alongside standard employee inputs. Process controllers set the action step to "complete" in Payroll Aggregator, which triggers a notification to External Partner. GT logs in with their restricted provider login and downloads an Excel spreadsheet containing all payroll inputs (tabs: pay data, new hires, leavers, changes). This integration is unchanged - the agent adds intelligence upstream but does not alter the Payroll Aggregator → GT interface.
5
Discrepancy Review - Investigator runs Claude Code skills 🔧 Skills
When GT returns results, Payroll Aggregator surfaces flagged discrepancies in the reconciliation view. The investigator opens a terminal or Claude.ai/code alongside Payroll Aggregator and runs skills by pasting the case or employee ID. /investigate <case-id> returns an instant plain-language breakdown of the delta and its likely significance. /root-cause <case-id> classifies the discrepancy across 6 categories - data entry error, timing difference, rate change, retroactive adjustment, provider calculation difference, or system mapping issue - and cites the specific records supporting each. /case-history <emp-id> retrieves this employee’s prior discrepancy record and how similar cases were resolved. /deep-dive <emp-id> pulls the full cross-system profile: HR / ERP System master record and Payroll Aggregator transaction history side-by-side. /draft-resolution <case-id> generates an accept/reject recommendation with supporting rationale, ready for the investigator to confirm or edit. /similar-cases <case-id> scans the current and prior cycles for matching discrepancy patterns across all employees. All reads go through MCP tools calling the Payroll Aggregator and HR / ERP System APIs - no Payroll Aggregator UI embedding. Each skill returns in seconds; what previously required 20-30 minutes of cross-system lookups takes under 3 minutes. The investigator makes every resolution decision - no autonomous write, no batch wait.
6
Discrepancies resolved - payroll run approved Unchanged
Once the investigator has accepted or rejected all flagged discrepancies in Payroll Aggregator, the payroll team gives final approval for the run. Because the investigator had full tool-assisted context at each decision point, approval confidence is higher and the compliance audit trail is richer than in the as-is state - every tool invocation, result, and resolution decision is logged automatically.
7
Payroll approved - Payslips & GL distributed Mostly unchanged
Once all discrepancies are resolved: External Partner uploads a PDF containing all payslips to Payroll Aggregator, which integrates them back into HR / ERP System so each employee has a Payroll Aggregator on their profile. A GL file in CSV format is generated in Payroll Aggregator and transferred to ERP / GL System via SFTP. In to-be, a utility skill auto-splits any GL file exceeding 1,000 lines (e.g. Sweden) before SFTP transfer, eliminating a recurring manual task. The agents have already done their work upstream; the payroll team has more confidence and a complete audit trail at this point than in the as-is state.
